# Core Design Principles

The page would show the information for reader from a lot of age groups and diverse backgrounds. Due to that, aim for universally readable design which apply the following principles.

### Adopt a Strict and Progressive Content Hierarchy

1. Starts with a lead section followed by several body sections.
2. Employs a predictable, hierarchical content flow that guides users from general to specific information.

### Online Images

Images are a crucial concept of the web, always add an image if there are anything that fits with an image.

1. Always use images in a generous amount, always have at least one image per page.
2. When deciding which images to choose, **always use oursourced images from an url whenever possible**. or a custom SVG element if it is not possible.
3. For now due to API limitation, for each image, search image from external url that fits the context of the image, if there are no appropriate external url, use placeholder Lorem Ipsum images with the following format. `https://picsum.photos/{width}/{height}?random={n}`
4. Make sure there are no repeating images.

### Visual Style — Modern Minimalist (Theme-Aware)

Aim for modern minimalistic UI. With a lots of images to aid scanning — not gratuitous decoration.

1. For each sections, use Content-Driven Container Selection. Follow the industry standards on which layout that should apply to a sections.
   1.1. Add proper spacing to add breathing room for scanning. Avoid congested information.
   1.2. Chunk information into a proper cohesive structure to reduce cognitive load.
   1.3. Aim to establish a F-shaped reading pattern through clear typography scale and color contrast.
2. **Unless for highlighting, strictly use only one shades of color**.
3. Minimal visual noise in the content area. Something such as excessive gradient should be avoided.
4. Separate informations into multiple sections and use typography such as heading and to differentiate information.
5. Each section should starts with a title, with `<h1>` for lead section and `<h2>` for the rest, without any emoji or icons if possible
6. Each section is wrapped with `<section>` tags, without any decorative wrapper like card.
7. When you are adding a new container, make sure it is outlined properly with borders or distinct background shades.
   7.1. **Section spacing must not exceed `p-5`** between adjacent sections — use `mb-5` or `gap-5` at most. Excess spacing (e.g. `my-6`, `my-8`, `gap-6`, `space-y-6`) creates unnecessary scroll distance and breaks the cohesive reading flow. A maximum of `16 px` (`p-5`) spacing ensures each section feels connected while still visually distinct.
8. **Prefer lightweight layouts over cards.** Cards (`rounded-[20px] [background:var(--color-surface)] p-3/p-4` as defined in `07-harmony-static-style-spec.md`) add visual weight and spacing overhead. Use them sparingly — only when data items demand a distinct visual boundary (e.g. a product with image + price + CTA). For simpler content groupings, choose one of the lighter alternatives below. **Card usage cap: no more than half of the sections on a page may use card layout** — e.g. if a page has 5 sections, at most 2 may contain card-style containers. The remaining sections must use lighter alternatives (Patterns A–E below, or plain section flow). This prevents the page from becoming a dense grid of visually heavy card blocks and preserves the minimalist, scan-friendly reading experience. **Prefer spacious card layouts when card is needed**, but the **Inline chip / tag row (Pattern D)** is also a good choice when the information is compact enough to fit within small tag-shaped containers.
9. **Apply rounded corners ONLY to pure cards.** Tables, grids (CSS Grid), flex layouts, list items, dividers, and block containers must NOT use `rounded-[20px]` or any large border-radius. The only exceptions are small inline chip/tag elements which may use `rounded-md` (6 px) at most. Rounded corners visually signal a self-contained card object — applying them to non-card layouts creates false visual grouping and unnecessary decoration.
10. For a round items within a list like layout, ensure that the round item has big enough radius for spacing.
11. **Grid layout integrity (MUST):** When using CSS Grid (`grid grid-cols-*`), every row must be fully populated. If the last row has fewer items than the column count, the final item must span across the remaining empty columns using `col-span-{n}` (where `n` = remaining empty columns + 1). Never leave orphaned empty cells — a grid with incomplete rows creates a broken, unbalanced visual. For dynamic or unknown-length data, prefer `grid-cols-1` and let items stack vertically instead.
12. Don't use too many emoji as it could create visual noise.

### ── Theme System (MUST) ──

All color references throughout these prompts MUST use the **theme variable tokens** defined below, not hardcoded hex values. The host shell injects CSS custom properties on `#root` to apply the active theme. This allows the color scheme to be swapped (e.g. Light Mode, High Contrast, custom palette) without regenerating prompt content.

**How to use theme tokens in Tailwind:**
Use Tailwind arbitrary-value syntax with `var()`:

| Token | Tailwind arbitrary-value usage |
|-------|-------------------------------|
| `--color-page-bg` | `[background:var(--color-page-bg)]` |
| `--color-surface` | `[background:var(--color-surface)]` |
| `--color-elevated` | `[background:var(--color-elevated)]` |
| `--color-border` | `[border-color:var(--color-border)]` / `[--tw-divide-opacity:1]` with color |
| `--color-text-heading` | `[color:var(--color-text-heading)]` |
| `--color-text-primary` | `[color:var(--color-text-primary)]` |
| `--color-text-secondary` | `[color:var(--color-text-secondary)]` |
| `--color-text-tertiary` | `[color:var(--color-text-tertiary)]` |
| `--color-accent` | `[background:var(--color-accent)]` / `[color:var(--color-accent)]` |
| `--color-accent-hover` | for hover/focus states |
| `--color-success-bg` / `--color-success-text` | semantic state backgrounds/texts |
| `--color-warning-bg` / `--color-warning-text` | semantic state backgrounds/texts |
| `--color-error-bg` / `--color-error-text` | semantic state backgrounds/texts |
| `--color-info-bg` / `--color-info-text` | semantic state backgrounds/texts |

When Tailwind's `divide-*` or `border-*` utilities are needed with theme colors, use arbitrary values like `[border-color:var(--color-border)]` and `divide-[color:var(--color-border)]` (the `divide-[color:...]` syntax works in Tailwind JIT).

For background and text, use `[background:var(--color-X)]` and `[color:var(--color-X)]` respectively.

When no theme is explicitly selected, the host defaults to these values:

**Important rules:**
- **Always write HTML using `var(--color-*)` tokens, not raw hex values.** The only exception is opacity modification on the accent color (see below).
- The tokens are abstract. A different theme (e.g. Light Mode) would inject different hex values into the same tokens.
- For opacity adjustments on accent colors (the only allowed color modification), use: `rgba(from var(--color-accent) r g b / 0.8)` (modern CSS color function) or simply apply Tailwind opacity utilities like `opacity-80` on the element.

### Background Correctness Rule for Card and Table Cell Containers (MUST)

A common rendering error occurs when card containers or table cells have **no explicit background token**, causing them to be transparent and invisible against the dark page background. Follow these rules to ensure every container has the correct surface colour.

**Pure card background layering:**
- A card at the page level always uses `[background:var(--color-surface)]` — this sits above `[background:var(--color-page-bg)]` on the outermost page.
- A card nested **inside** another card (or inside a container that already uses `[background:var(--color-surface)]`) must use `[background:var(--color-elevated)]` instead, so the inner card remains visibly distinct from its parent surface.
- A card placed inside a `<section>` that inherits the page background (no explicit background of its own) should use `[background:var(--color-surface)]` as normal.
- **Never omit the background token on a card container** — every card must have an explicit `[background:var(--color-surface)]` (or `[background:var(--color-elevated)]` if nested).

**Table header and data cell backgrounds:**
- A `<thead>` row must use `[background:var(--color-elevated)]` on `<tr>` or `<th>` elements to visually separate column heads from data rows.
- Data rows in `<tbody>` should use one of the following patterns:
  - **Same solid background for table cell contains** `[background:var(--color-surface)]`, OR
  - **Plain border separation**: no background on any data row, relying on `divide-y [border-color:var(--color-border)]` to separate rows (Pattern A approach).
- Always set the background on the `<tr>` level, not on individual `<td>`/`<th>` cells, so background inheritance is consistent.
- For interactive (hoverable) table rows, use `hover:[background:var(--color-elevated)]` on the `<tr>`.

**Self-check:** Before finalising any card or table, verify that every container has an explicit theme-token background (`var(--color-surface)` or `var(--color-elevated)`) or is deliberately transparent. A missing background causes the element to appear invisible or mismatched against the dark page background.

### Layout Alternatives to Cards (MUST) — Theme-Aware

To avoid congested output and unnecessary visual weight, **always prefer these card-free patterns** before reaching for a card container. Use the simplest pattern that adequately structures the content. All examples use theme variable tokens instead of hardcoded colors. It is highly preferred to use these pattern without any rounded corners.

**Pattern A — Plain vertical list (no container wrapper, no rounded corner and no border radius)**

```
<div class="flex flex-col divide-y [border-color:var(--color-border)]">
  <div class="py-4 [color:var(--color-text-primary)]">
    Item 1
  </div>
  <div class="py-4 [color:var(--color-text-primary)]">
    Item 2
  </div>
  <div class="py-4 [color:var(--color-text-primary)]">
    Item 3
  </div>
</div>
```
- Best for: text-heavy lists, link lists, article summaries, timeline entries.
- No background, no rounded corner and no border radius, no padding wrapper — just `divide-y` or `border-b` with `[border-color:var(--color-border)]` on items.
- Each item uses `py-3` (12 px) or `py-4` (16 px) for touch-friendly vertical spacing.
- Text uses `[color:var(--color-text-primary)]` (primary) or `[color:var(--color-text-secondary)]` (secondary/meta).

**Pattern A.2 — Numbered vertical list (no container wrapper, no rounded corner and no border radius)**

```
<div class="flex flex-col divide-y [border-color:var(--color-border)]">
  <div class="py-4">

    <p class="[color:var(--color-text-primary)]">Item 1</p>
  </div>
  <div class="py-4">
    <span class="[color:var(--color-text-secondary)] text-xs w-12 h-12">Label</span>
    <p class="[color:var(--color-text-primary)]">Item 2</p>
  </div>

    <span class="[color:var(--color-text-secondary)] text-xs w-12 h-12">Label</span>
    <p class="[color:var(--color-text-primary)]">Item 3</p>
  </div>
</div>
```
- Best for: text-heavy lists, link lists, article summaries, timeline entries.
- No background, no rounded corner and no border radius, no padding wrapper — just `divide-y` or `border-b` with `[border-color:var(--color-border)]` on items.
- Each item uses `py-3` (12 px) or `py-4` (16 px) for touch-friendly vertical spacing.
- Text uses `[color:var(--color-text-primary)]` (primary) or `[color:var(--color-text-secondary)]` (secondary/meta).


**Pattern B — Horizontal flex row with border separators (no rounded corner and no border radius)**
```
<div class="flex divide-x [border-color:var(--color-border)]">
  <div class="flex-1 min-w-0 px-4">
    <span class="[color:var(--color-text-secondary)] text-xs w-12 h-12">Label</span>
    <p class="[color:var(--color-text-primary)] text-sm font-medium">Value</p>
  </div>
  <div class="flex-1 min-w-0 px-4">
    <span class="[color:var(--color-text-secondary)] text-xs w-12 h-12">Label</span>
    <p class="[color:var(--color-text-primary)] text-sm font-medium">Value</p>
  </div>
  <div class="flex-1 min-w-0 px-4">
    <span class="[color:var(--color-text-secondary)] text-xs w-12 h-12">Label</span>
    <p class="[color:var(--color-text-primary)] text-sm font-medium">Value</p>
  </div>
</div>
```
- Best for: stat/metric grids (3–4 values side by side), comparison columns, key-value pairs.
- Uses `divide-x` with `[border-color:var(--color-border)]` for vertical separators instead of card backgrounds.
- Each cell gets `px-3` or `px-4` horizontal padding; no background fill needed.
- On mobile, if 4+ columns, wrap with `flex-wrap` and let items stack 2-per-row.
- No background, no rounded corner and no border radius, no padding wrapper.

**Pattern C — Minimal bordered block (no rounded corner and no border radius)**
```
<div class="border [border-color:var(--color-border)] p-4">
  <!-- content -->
</div>
```
- Best for: when a visual boundary is needed but a full card feels too heavy.
- Uses only `border [border-color:var(--color-border)]` + `p-3`/`p-4` — no `[background:var(--color-surface)]`, no `rounded-[20px]`, no `shadow`.
- The border subtly defines the region against the page background without adding card-like visual mass.
- No rounded corner and no border radius, no padding wrapper. Whenever fits, consider using no border.

**Pattern D — Inline chip / tag row**
```
<div class="flex flex-wrap gap-2">
  <span class="inline-block border [border-color:var(--color-border)] rounded-md px-3 py-1 text-xs [color:var(--color-text-secondary)]">Tag A</span>
  <span class="inline-block border [border-color:var(--color-border)] rounded-md px-3 py-1 text-xs [color:var(--color-text-secondary)]">Tag B</span>
  <span class="inline-block [background:var(--color-elevated)] px-3 py-1 text-xs [color:var(--color-text-secondary)]">Tag C</span>
</div>
```
- Best for: metadata, categories, filter tags, keyword clusters.
- Compact but spacious enough for touch: `py-1` + `px-3` minimum.
- No card wrapper — just the chip elements themselves with a `[border-color:var(--color-border)]` border or `[background:var(--color-elevated)]` tinted background.
- **When to use chips vs cards:** Chips (Pattern D) are more favourable than a full card when the information is **single-dimensional** — e.g. a list of category labels, filter options, status badges, keyword tags, or short numeric summaries. A card would add excessive visual weight for such lightweight data. However, if each item contains **2+ content layers** (e.g. a label + a value + a description), a card or bordered block (Pattern C) is preferable for readability.

**Pattern E — Timeline / chronological list (no rounded corners, no card background)**

```
<div class="flex flex-col [border-color:var(--color-border)]">
  <div class="relative flex gap-4 pb-6">
    <div class="flex flex-col items-center shrink-0">
      <div class="w-3 h-3 rounded-full [background:var(--color-accent)]"></div>
      <div class="w-px flex-1 [background:var(--color-border)]"></div>
    </div>

      <span class="[color:var(--color-text-heading)] text-sm font-medium">Event title</span>
      <p class="[color:var(--color-text-secondary)] text-xs mt-1">Event description or details.</p>
    </div>
  </div>
  <div class="relative flex gap-4 pb-6">
    <div class="flex flex-col items-center shrink-0">
      <div class="w-3 h-3 rounded-full [background:var(--color-accent)]"></div>
      <div class="w-px flex-1 [background:var(--color-border)]"></div>
    </div>
    <div class="flex-1 min-w-0 pb-2">
      <span class="[color:var(--color-text-heading)] text-sm font-medium">Another event</span>
      <p class="[color:var(--color-text-secondary)] text-xs mt-1">Another description.</p>
    </div>
  </div>
  <div class="relative flex gap-4">
    <div class="flex flex-col items-center shrink-0">
      <div class="w-3 h-3 rounded-full [background:var(--color-accent)]"></div>
    </div>
    <div class="flex-1 min-w-0">
      <span class="[color:var(--color-text-heading)] text-sm font-medium">Final event</span>
      <p class="[color:var(--color-text-secondary)] text-xs mt-1">No connector line after the last item.</p>
    </div>
  </div>
</div>
```
- Best for: chronological sequences, step-by-step processes, history, release notes, event timelines.
- Uses a vertical connector line (`w-px [background:var(--color-border)]`) with accent-coloured dots (`w-3 h-3 rounded-full [background:var(--color-accent)]`) as timeline markers.
- The last item omits the connector line (no trailing divider).
- Each timeline item uses `gap-4` horizontal spacing between the dot column and the content column.
- No background, no rounded corners (except the dot itself which is `rounded-full`), no padding wrapper.
- Text uses `[color:var(--color-text-heading)]` for the event title and `[color:var(--color-text-secondary)]` for the description.

**When to use a full card (07-harmony-static-style-spec.md)**
Only reach for `rounded-[20px] [background:var(--color-surface)] ...` when:
- The item contains **3+ distinct content layers** (e.g. image + title + description + button).
- The item needs to be visually separable from a busy background or adjacent items.
- The user explicitly requests a "card" layout.

Otherwise, use Pattern A, B, C, D, or E above.

### Typography System (MUST) — Theme-Aware

- Font stack: `HarmonyOS Sans, PingFang SC, system-ui, sans-serif` (HarmonyOS-like sans stack).
- Minimum readable font size is **10 px**.
- Size hierarchy (use Tailwind `text-xs`/`text-sm`/`text-base`/`text-lg`):
  - Title / summary: `30`–`35 px`, `font-medium` or `font-semibold`.
  - Body / list: `20`–`24 px`.
  - Meta / tag / caption: `14`–`16 px`.
- Text‑color hierarchy uses theme tokens:
  - **Heading / title**: `[color:var(--color-text-heading)]`
  - **Primary text** (body): `[color:var(--color-text-primary)]`
  - **Secondary text** (meta, descriptions, labels): `[color:var(--color-text-secondary)]`
  - **Tertiary text** (captions, disabled, hints): `[color:var(--color-text-tertiary)]`
- **Contrast the text accordingly** — ensure sufficient contrast ratio against the current background. Avoid text below `var(--color-text-tertiary)` for body content.
- The overall page follows the **one shade** rule (§Visual Style 2). Inside card components, low‑opacity tints for **semantic state** blocks (success, warning, error) are permitted — see `07-harmony-static-style-spec.md` §7.

### Color Scheme — Theme Token Reference

All colors are accessed through CSS custom properties (theme tokens). The host injects these on `#root`. The overall page follows the **one shade** rule from Visual Style (§2) — pick **one** accent hue as the page's single primary accent; use other hues **only** for semantic state indicators (success/warning/error/info) and only in small, scoped blocks.

**Page background:** `[background:var(--color-page-bg)]`

**Neutral surface tokens:**

| Token | Default (Dark Mode) | Role |
|-------|-------------------|------|
| `--color-page-bg` | `#0A0A0A` | Page background / outermost container |
| `--color-surface` | `#1A1A1A` | Card container surface, section backgrounds |
| `--color-elevated` | `#2A2A2A` | Elevated surface (inset blocks, hover states, chips) |
| `--color-border` | `#333333` | Subtle borders, dividers |
| `--color-text-tertiary` | `#666666` | Tertiary text, disabled, placeholders |
| `--color-text-secondary` | `#999999` | Secondary text, meta, descriptions, labels |
| `--color-text-primary` | `#CCCCCC` | Primary body text |
| `--color-text-heading` | `#E5E5E5` | Strong headings, titles |

**Important rule:** When nesting surfaces, use `[border-color:var(--color-border)]` to separate adjacent layers. A container `[background:var(--color-surface)]` inside page `[background:var(--color-page-bg)]` already has contrast; two `[background:var(--color-surface)]` siblings need border or `[background:var(--color-elevated)]` differentiation.

**Accent hues** (the `--color-accent` token can be set to any of these values to change the page accent):

| Name | Hex | Notes |
|------|-----|-------|
| Blue (brand) | `#0A59F7` | Default `--color-accent` |
| Green | `#00A870` | |
| Gold | `#D4A017` | |
| Red | `#E84026` | |
| Purple | `#7C4DFF` | |
| Cyan | `#1EC8C8` | |

You may **modify an accent colour by changing its opacity only** (e.g. `rgba(from var(--color-accent) r g b / 0.8)`). Do **not** change the hue, saturation, or lightness of the base hex.

**Semantic state tints** (allowed as exceptions to the one‑shade rule):

| State | Background token | Text token |
|-------|-----------------|------------|
| Success | `var(--color-success-bg)` | `var(--color-success-text)` |
| Warning | `var(--color-warning-bg)` | `var(--color-warning-text)` |
| Error | `var(--color-error-bg)` | `var(--color-error-text)` |
| Info | `var(--color-info-bg)` | `var(--color-info-text)` |

Default (Dark Mode) values: Success `#1A2E1A` / `#4ADE80`, Warning `#2E2A1A` / `#FBBF24`, Error `#2E1A1A` / `#F87171`, Info `#1A1E2E` / `#60A5FA`.

### Specific Rules for Lead Section (Theme-Aware)

1. Always start this section with a centered title, without any emoji or icons if possible. Additional subtitles is also permitted. **Must include at least one image** (hero‑style, below or beside the title) to create immediate visual impact. Additional paragraph is preferred.
2. **No unnecessary repeating information from the user prompt** -- instead depending on the topics, add either a summary, a preface, an introduction, some fun facts, or crucial information **in paragraph format** about what will be described in the next sections. Avoid unnecessary chips or cards.
3. Provides immediate context without requiring scrolling.
4. Answers the user's primary query in 1-3 sentences and provide enough connecting statements to the next sections.
5. **Spacing rule**: The lead section must have extra vertical padding (`py-10` or `py-12`) so it feels like a deliberate entry point, not a cramped header.
6. **No card wrapper**: The lead section content must not be wrapped in a card container — use plain section-level flow with direct children.
7. **Background**: The lead section sits on the page-level `[background:var(--color-page-bg)]`. Use `[color:var(--color-text-heading)]` for the title and `[color:var(--color-text-secondary)]` for the subtitle/summary. The hero image should be bright/well‑lit so it stands out against the background.

### Semantic HTML Foundation

Leverages the semantic HTML5 elements to enhance readability.

> **Note on typography:** For inline text styling (bold, italic, underline etc.), follow the `<span>`-based mapping in `10-css-and-html-subsets-categories.md` §2 instead of semantic HTML tags.
